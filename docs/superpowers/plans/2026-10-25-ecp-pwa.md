# Ewidencja czasu pracy — PWA: plan implementacji

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Instalowalna aplikacja PWA dla pracowników i admina GROUP-ON-VET, zapisująca dane do istniejącego arkusza przez nowe API `doPost` w Apps Script, z kolejką offline.

**Architecture:** Statyczna PWA (`pwa/`, GitHub Pages) woła `POST text/plain` JSON na osobne wdrożenie Apps Script. Nowy plik `apps-script/api.gs` weryfikuje token HMAC, sprawdza uprawnienia według jawnej tabeli akcji i woła istniejące funkcje GS bez ich zmieniania. Telefon trzyma kolejkę zapisów i cache odczytów w IndexedDB.

**Tech Stack:** Google Apps Script (V8); czysty HTML/CSS/JS (ES modules, bez bundlera); Node 24 `node:test` do testów; `fake-indexeddb` (devDependency); Python PIL do ikon; GitHub Actions Pages.

**Spec:** `docs/superpowers/specs/2026-10-25-ecp-pwa-design.md`

## Global Constraints

- Istniejący kod GS, `form`, `admin`, `karta` i istniejące wdrożenie — **bez zmian**. `api.gs` dodaje tylko `doPost` i nazwy z prefiksem `api` (publiczne: `apiSetup`, `apiWylogujWszystkich`, `apiLogCleanup`; prywatne: `api…_`).
- `pracownikId` zawsze z tokenu; argument klienta o tej nazwie jest usuwany przed wywołaniem funkcji GS.
- Rola czytana przy każdym żądaniu z kolumny arkusza `Pracownicy` o nagłówku „Rola” (wiersz 1, bez względu na wielkość liter / spacje; brak kolumny = wszyscy pracownik); `admin` (bez względu na wielkość liter / spacje) = admin. Kolumny G i H to limity urlopu — nie ruszać. *(Zmienione po przeglądzie końcowym — wcześniej błędnie kol. G.)*
- Token: `base64WebSafe(JSON{id,exp}) + "." + base64WebSafe(HMAC-SHA256)`, ważność 30 dni; sekret w Script Properties `API_SECRET`.
- Blokada PIN: 5 błędów / urządzenie → 15 min; 30 błędów globalnie → 15 min (CacheService, TTL 900 s).
- Idempotencja: ukryty arkusz `API_Log` (A clientId, B czas, C pracownikId, D akcja, E wynik JSON), `LockService` script lock, czyszczenie wpisów > 60 dni dziennym wyzwalaczem.
- Kody błędów: `AUTH`, `FORBIDDEN`, `BAD_REQUEST`, `REJECTED`, `LOCKED`, `SERVER`. (Doprecyzowanie spec §5.1: `REJECTED` = funkcja GS zwróciła `{ok:false}` — błąd merytoryczny; `LOCKED` = blokada PIN.)
- Kolejkowane (offline): tylko `zapiszGodziny`, `zapiszUrlop`, `zapiszWyjscie`. Korekty, usuwanie i cały panel admina — tylko online.
- Limit `fetch`: 30 s; akcje `pdf*` i `mojaKarta`: 60 s.
- UI po polsku, kolor główny `#1a56db`, Arial; komunikaty bez technicznych błędów.
- Do repozytorium nie trafiają `.docx` ani `reference/` (repo będzie publiczne).

## Review Focus

1. Dwa szybkie tapnięcia „Zapisz” / wysyłka kolejki przerwana po zapisie, przed odpowiedzią → w arkuszu ma być jeden wiersz (test w Task 3: ten sam `clientId` dwa razy → jeden `appendRow`; test w Task 5: `flush()` wywołane równolegle wysyła element raz).
2. Token wygasły lub podrobiony w trakcie synchronizacji → kolejka nietknięta, prośba o PIN, po zalogowaniu wysyłka (Task 1: test podrobionego/wygasłego; Task 5: test `AUTH` zatrzymuje i zachowuje).
3. Pracownik usunięty z arkusza / odebrana rola admina przy ważnym tokenie → natychmiast `AUTH` / `FORBIDDEN` (Task 1).
4. Daty z arkusza (`Date`) w odpowiedzi → tekst, nie `{}` / przesunięta strefa (Task 1: test `apiSerialize_` dla daty północnej i z godziną).
5. Zapis offline z formularza z błędem merytorycznym (np. od > do w wyjściu) → wpis ❗ z komunikatem serwera, nie zapętlone ponawianie, pozostałe wpisy idą dalej (Task 5; ręcznie w Task 7).

### Task 5: Silnik synchronizacji

**Files:**
- Create: `pwa/js/sync.js`
- Test: `tests/sync.test.mjs`

**Interfaces:**
- Consumes: `store.js` (outbox*), `createApi().call`, `NetworkError`
- Produces: `createSync({store, api, onChange: (items) => void, newId = () => crypto.randomUUID()}) → { enqueue(action, args) → Promise<item>, replace(clientId, action, args) → Promise<item>, discard(clientId), flush() → Promise<void>, list() → Promise<item[]> }`
  - `enqueue` dodaje `pending`, woła `onChange`, potem `flush()` (bez czekania na sieć w wywołującym — zwraca item po zapisie lokalnym)

  - `flush`: single-flight (równoległe wywołania dzielą jedną obietnicę); elementy `pending` po kolei: `ok` → usuń; `REJECTED`/`BAD_REQUEST`/`FORBIDDEN` → `status:'error'`, `error` = komunikat serwera, idź dalej; `AUTH`, `SERVER`, `NetworkError` → przerwij, zostaw element; elementy `error` pomijane. Po każdej zmianie `onChange(await list())`.

  - `REJECTED` na 1. elemencie → 1. `error` z komunikatem, 2. wysłany i usunięty
  - `NetworkError` → przerwanie, oba zostają `pending`
  - `AUTH` → przerwanie, element zostaje `pending`
  - dwa równoległe `flush()` → `call` raz na element
  - `replace` usuwa element `error` i kolejkuje nowy `pending`
